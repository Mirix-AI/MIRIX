# graph_v7.1_clean — the v7.1 / v7.2 retrieval variants, made measurable

This branch restores the graph retriever as it stood on 2026-07-03, because it holds one
thing the mainline no longer does: **two different rerank strategies, side by side**.

It is not a candidate for merging. It exists so that one question can be answered.

---

## Why this branch exists

`shdoc_v71` scored 87/100 on SHDocQA — the highest of that whole batch, above no-graph (83),
v7 (83), v8 (85) and v8.1 (82). That looks like "v7.1 is the best version", and it is not.

Reading the code explains the shape. The retriever gated its rerank on `== "v7.1"`, so v7.3,
v7.10, v8 and v8.1 all silently fell through to unranked traversal-order truncation. The
`shdoc_v71` result is measuring **rerank versus no rerank**, not v7.1 versus v8. The equality
was later widened to "v7.1 and above", which is why v7.23 reranks today, and the standalone
toggle `MIRIX_GRAPH_RERANK=0/1` now exists to measure that directly.

What did NOT survive the rewrite is v7.2:

```python
if settings.graph_version == "v7.2":
    # per-anchor coverage rerank. Rerank each matched anchor's own candidates
    # (v7.1's single pooled rerank collapses onto one entity — good for
    #  a single-entity question, bad when the answer spans several)
    ep_rows, sem_rows = await self._retrieve_coverage(...)
else:
    # v7.1: one pooled rerank over everything the anchors collected
    rerank = q_emb if settings.graph_version == "v7.1" else None
```

The mainline kept the pooled version and dropped the per-anchor one. **Nobody measured which
is better on a clean setup.** That is the open question this branch is for.

## What was changed to make it usable

Two commits on top of `b77b025`, both about measurability rather than behaviour:

**A storage namespace.** This era wrote every PG row and every graph node under the bare
LoCoMo conversation id. That is where the shared Neo4j's unprefixed `conv-42` / `conv-43` /
`conv-48` namespaces come from — 1508 nodes still sit under bare `conv-30` today. A run on
the mainline that misspelled its own prefix variable later landed on 959 of those anchors and
produced a plausible-looking 0.882 against data it had not created. `MIRIX_EVAL_USER_PREFIX`
now moves ownership in PG and Neo4j while leaving `sample_id` and result filenames alone.

Verified on a smoke run: the server logs `user_id=v71s2__conv-30` where it previously logged
`conv-30`, PG rows land under `v71s2__conv-30`, and the graph writes `V7Anchor` and
`V7MemoryRef` nodes under the same prefix while bare `conv-30` does not grow.

**Decontaminated prompts.** The extraction prompts and the answerer's few-shot examples
carried LoCoMo gold answers until 2026-08-04 — "Becoming Nicole", "clarinet and violin", the
Melanie/Caroline pair. Anything measured on this branch before that fix was comparing a
system against answers it had been shown. The three prompt files come from the mainline fix.
`task_agent.py` is patched entity by entity rather than replaced, because the current file
carries 870 lines of v7.20-v7.24 policy code whose modules do not exist here.

## How to run it

```bash
git worktree add /tmp/v71 graph_v7.1_clean
cd /tmp/v71

# a database of its own — never share one with a mainline run
createdb -T template0 mirix_v71_a
psql -d mirix_v71_a -c "CREATE EXTENSION IF NOT EXISTS vector;"

MIRIX_PG_DB=mirix_v71_a MIRIX_GRAPH_VERSION=v7.1 MIRIX_ENABLE_GRAPH_MEMORY=true \
  python scripts/start_server.py --port 8531

cd evals
export MIRIX_PG_DB=mirix_v71_a MIRIX_GRAPH_VERSION=v7.1 \
       MIRIX_ENABLE_GRAPH_MEMORY=true MIRIX_EVAL_USER_PREFIX=v71a__
python main_eval.py --data data/locomo_c30.json --run-llm \
  --mirix_config_path ./configs/0201c_v6.yaml --output_path v71_arm
python organize_results.py --judge default results/locomo/v71_arm
```

Swap `MIRIX_GRAPH_VERSION=v7.2` and a fresh `MIRIX_EVAL_USER_PREFIX` for the other arm. Both
arms need their own prefix or the second silently reads the first one's graph.

`evals/data/` is not in this branch's tree — copy the datasets across from the mainline.

## What a number from here can and cannot be compared to

**Can:** v7.1 against v7.2, on the same store, same prompts, same day. That is the whole
point.

**Cannot:** anything on the mainline. This predates the v7.12 n-ary frame rewrite, six
AutoDream variants and five retrieval policies. It still writes `V7MemoryRef` nodes, a layer
v7.12 removed entirely. A store built here is its own.

**Also cannot:** the historical `shdoc_v71` 87/100. That run used contaminated prompts, no
storage prefix, and its own v7-era store. Re-running v7.1 here will not reproduce it, and
should not be expected to.

## If you run the comparison, run it properly

The mainline handover (`evals/HANDOVER.md` on `graph_revision`) has the measurement rules,
and they apply here unchanged. The two that matter most:

- **Do not subtract two accuracies.** Use McNemar on the discordant pairs. Two identical
  QA-only runs over one store differ by 9-15 questions on 1540 because Neo4j's vector search
  is not deterministic, so a difference smaller than that means nothing without pairing.
- **Assert before every arm** that rows exist under the expected prefix and nothing sits
  outside it. Three runs on the mainline produced plausible numbers while not running the
  experiment at all.

v7.1 versus v7.2 is a retrieval-side question, so it can be answered QA-only against one
store: ingest once, then answer twice with the version string flipped. That removes ingest
drift, which is the larger of the two noise sources.
